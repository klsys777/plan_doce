# EMB_EC_CAN_Motor EtherCAT 协议总结

整理日期：2026-11-09。依据 `EMB_EC_CAN_Motor` 当前源码和 `ESI/GDESC_IO.xml` 静态分析，源码提交为 `92d356cd5bef12753182d75a5a34ee78e6f5f2de`。本文描述该参考项目的实际实现，不是灵巧手 21 关节新协议，也不把厂家协议文档中列出的功能等同于固件已实现功能。未进行编译、抓包或硬件验证。

## 1. 协议概貌

该工程是一个 EtherCAT 从站到三路 CAN 的电机报文桥接器。主站通过固定 PDO 下发 24 个电机槽的 8 字节报文，MCU 根据预设槽位选择 CAN 通道发送；收到符合条件的 8 字节电机应答后，原样写回对应 TxPDO 槽。

| 项目 | 当前实现 |
| --- | --- |
| MCU / ESC 接口 | GD32H75E，OSPI 访问 ESC |
| EtherCAT 栈 | Beckhoff SSC，配置显示版本 5.13 |
| 设备名 | `GDESC_IO_motor` |
| 最大槽数 | 24；CAN0、CAN1、CAN2 各 8 槽 |
| 主站 → 从站 | RxPDO `0x1600`，映射 `0x7010`，208 B |
| 从站 → 主站 | TxPDO `0x1A00`，映射 `0x6000`，236 B |
| 命令处理门控 | UINT64 `hs` 更新条件 + `control_word == 1` |
| 电机数据 | 每槽固定 8 B，具体位定义、单位由电机厂家协议决定 |
| 专用操作 | 首次使能、全 FF 条件下选择性置零 |
| 反馈诊断 | 三路通信缺帧位、使能 / 置零成功位、CAN 硬件错误计数 |

不存在本文所能确认的“统一位置 / 速度 / 电流 REAL32 对象”。`motor_n` 虽然在对象字典中声明为 UINT64，但实际作为 8 字节原始报文使用。

## 2. 固定槽位与编译配置

### 2.1 槽位路由

对槽号 `n=1..24`：

```text
内部索引 i = n - 1
CAN 通道 = i / 8              // 0、1、2
本通道槽号 j = i % 8          // 0..7
普通发送 CAN ID = n           // 全局编号，不按通道重新从1编号
发送邮箱 = 8 + j
普通接收邮箱 = j
专用使能 / 置零回复邮箱 = 16，CAN ID = 0x7FF
Rx / Tx 中 motor_n 起始字节 = 8 + (n - 1) × 8
```

| 槽号 | 总线 | 普通发送CAN ID | Rx/Tx motor子索引（十进制） | Rx/Tx起始字节 |
| --- | --- | --- | --- | --- |
| 1 | CAN0 | `0x001` | 2 | 8+(1-1)×8 = 8 |
| 2 | CAN0 | `0x002` | 3 | 8+(2-1)×8 = 16 |
| 3 | CAN0 | `0x003` | 4 | 8+(3-1)×8 = 24 |
| 4 | CAN0 | `0x004` | 5 | 8+(4-1)×8 = 32 |
| 5 | CAN0 | `0x005` | 6 | 8+(5-1)×8 = 40 |
| 6 | CAN0 | `0x006` | 7 | 8+(6-1)×8 = 48 |
| 7 | CAN0 | `0x007` | 8 | 8+(7-1)×8 = 56 |
| 8 | CAN0 | `0x008` | 9 | 8+(8-1)×8 = 64 |
| 9 | CAN1 | `0x009` | 10 | 8+(9-1)×8 = 72 |
| 10 | CAN1 | `0x00A` | 11 | 8+(10-1)×8 = 80 |
| 11 | CAN1 | `0x00B` | 12 | 8+(11-1)×8 = 88 |
| 12 | CAN1 | `0x00C` | 13 | 8+(12-1)×8 = 96 |
| 13 | CAN1 | `0x00D` | 14 | 8+(13-1)×8 = 104 |
| 14 | CAN1 | `0x00E` | 15 | 8+(14-1)×8 = 112 |
| 15 | CAN1 | `0x00F` | 16 | 8+(15-1)×8 = 120 |
| 16 | CAN1 | `0x010` | 17 | 8+(16-1)×8 = 128 |
| 17 | CAN2 | `0x011` | 18 | 8+(17-1)×8 = 136 |

即使某槽配置为 `NONE`，其 8 字节仍占据固定 PDO 位置，不能压缩后续槽位。

### 2.2 当前默认与可选编译分组

`control.h` 中 `ENABLE_MCU1`、`ENABLE_CANFD`、`ENABLE_CANFD_LEADSHINE_SAMPLE_POINT` 均被注释；已查看的 Keil 工程 Define 为 `USE_STDPERIPH_DRIVER,GD32H75E`，未启用上述开关。

| 分组 | CAN0 有效电机 | CAN1 有效电机 | CAN2 有效电机 | 有效数量 |
| --- | --- | --- | --- | --- |
| 默认，未定义 ENABLE_MCU1 | 1～4 | 9～12 | 17～18 | 10 |
| 定义 ENABLE_MCU1 | 1～6 | 9～14 | 17～19 | 15 |

两组有效槽当前均设为 `LEADSHINE`，其余为 `NONE`。注释分别称默认组为“左右臂 + 头”，可选组为“左右腿 + 腰”。这只是编译分组，不是灵巧手的主 8 / 副 13 角色分工，也没有运行时 GPIO 角色锁定逻辑。

MotorType 枚举：NONE=1、DMBOT=2、INKEXBOT=3、LEADSHINE=4。代码包含其他厂家分支，但默认配置未使用它们。

默认电机链路为标准帧、经典 CAN、1 Mbit/s，FDF=0、BRS=0。启用 ENABLE_CANFD 后配置 CAN FD，仲裁段 1 Mbit/s、数据段 5 Mbit/s，并设置 FDF/BRS；普通发送载荷仍为 8 B。协议文件中存在 12 B CAN FD 应答并不意味着当前 EC 桥接能接收并上传它，见第 7 章。

## 3. EtherCAT 身份、同步与对象字典

### 3.1 身份配置及已发现差异

| 字段 | 固件配置 | ESI |
| --- | --- | --- |
| Vendor ID | `0x00000123` | `0x00000123` |
| Product Code | **`0x00000004`** | **`0x00000001`** |
| Revision | `0x00000001` | `0x00000001` |
| Serial number | `0x00000000` | 应核对实际 EEPROM / SDO 读回 |
| Device name | `GDESC_IO_motor` | `GDESC_IO_motor` |
| Device profile type | `0x00001389`，十进制 5001 | 模块化设备配置相关描述 |
| 硬件版本字符串 | `GDESC_Device` | 以实际设备读回为准 |
| 软件版本字符串 | `5.13` | 此字符串不能用于推断应用固件完整版本 |

Product Code 不一致是现有文件事实，使用主站时需核对实际烧录的 EEPROM、ESI 与 `0x1018`，不能直接认为三者一致。`APPL_GetDeviceID()` 返回固定 `0x5`，是模板显式设备 ID，不是动态读取的电机 ID 或 GPIO 角色。

### 3.2 SM 与同步模式

| SM | 用途 | ESI 默认起始地址 | 默认长度 |
| --- | --- | --- | --- |
| SM0 | MBoxOut，主站写邮箱 | `0x1000` | 128 B |
| SM1 | MBoxIn，主站读邮箱 | `0x1080` | 128 B |
| SM2 | Outputs，RxPDO | `0x1100` | 208 B |
| SM3 | Inputs，TxPDO | `0x1400` | 236 B |

ESI 邮箱最小 34 B、最大 256 B。支持 CoE SDO Info、Complete Access 和分段 SDO；`PdoAssign=false`、`PdoConfig=false`，RxPDO / TxPDO 标注 Fixed=true、Mandatory=true。

ESI 提供 SM-Synchron（AssignActivate=`0x0000`）和 DC-Synchron（`0x0300`）。Sync0 / Sync1 的 CycleTime 节点为 0、Factor=1，具体周期由主站配置。`MIN_PD_CYCLE_TIME=0x186A0` 表示声明最小周期 100000 ns，即 100 μs；这不是实测性能保证，也不能据此说项目固定在 1 kHz 运行。

### 3.3 应用对象

| 对象 | SI0 | 内容 / 分配 |
| --- | --- | --- |
| `0x1600` | 28 | RxPDO 固定映射条目 |
| `0x1A00` | 37 | TxPDO 固定映射条目 |
| `0x1C12` | 1 | SI1=`0x1600` |
| `0x1C13` | 1 | SI1=`0x1A00` |
| `0x6000` | 37 | 输入记录；对象字段声明只读 |
| `0x7010` | 28 | 输出记录；对象字段声明读写 |
| `0xF000` | 2 | SI1 Index distance=`0x10`；SI2 Maximum number of modules=0 |

本项目没有新灵巧手设计中的 `0x2000` 拓扑、`0x2100` 异步电机服务或按关节独立组织的命令对象。

映射值使用 `(index << 16) | (subindex << 8) | bit_length`。例如，Rx 的 motor_1 为 `0x70100240`，control_word 为 `0x70101B10`；Tx 的 can1_error_log 为 `0x60001B20`。SI0 不包含在 PDO 线上数据中。

### 4.1 hs：实际是命令序号门控

固件内部 `hs_` 初始为 0，只有下列条件满足时才执行本次控制：

```c
new_hs > hs_ || (new_hs == 1 && hs_ != 1)
```

- 相同 hs 被忽略，包括修改了其他字段但没有改变 hs 的情况。
- 小于旧值的 hs 通常被忽略；1 是特殊重新初始化值。
- 接受 hs=1 时，清 `is_enable`、三路 can_error_log 和 last_motor_command，然后按当前 control_word 执行。
- 接受后把 `hs_` 更新为 new_hs；即使 control_word 不等于 1、没有发送电机数据，也会更新 hs_。
- 启动时 hs=0 不触发控制；最大 UINT64 后不支持普通模计数回绕到 0，可用特殊 hs=1 重新进入初始化路径。
- 没有以墙钟或单调时钟实现的 hs 失联停机计时器。hs 不能解释为已经完整实现的通信心跳保护。

### 4.2 control_word

| 值 / 条件 | 当前行为 |
| --- | --- |
| 1 且 is_enable=0 | 发送一次初始化使能批次，随后直接返回，本次不发送普通电机槽数据 |
| 1 且 is_enable=1 | 调用 pack_motor_data，进入普通透传或置零分支 |
| 其他值，包括 0 | 不发送本次普通控制数据；没有主动失能报文，也不会把 is_enable 清零 |

这个字段不是 CiA 402 控制字，不能把 0 当成已实现的停机、失能或急停命令。

### 4.3 motor_enable 与 lz_3

`motor_enable` 仅在置零分支使用，bit(n−1)=1 选中槽 n 进行置零。它不限制首次使能批次，也不屏蔽普通透传。因此将它设置为 0 不能阻止普通控制帧发送。

`lz_3` 在布局中占 2 B，但当前控制代码没有读取它的业务逻辑。不能根据名称推断其设备功能，主站建议填 0。

## 5. 首次使能与置零规则

### 5.1 首次使能

进入 `control_word=1 && is_enable=0` 分支时：

| 电机类型 | 当前发出的 CAN 报文 |
| --- | --- |
| LEADSHINE | 标准 ID `0x7FF`，长度 4，`00 nn 00 06`，nn 为全局电机 ID 1～24 |
| DMBOT | 普通电机 ID，长度 8，`FF FF FF FF FF FF FF FC` |
| INKEXBOT | 此分支没有专门的使能发送实现 |
| NONE | 不发送 |

LEADSHINE 发送前清除对应的使能成功位。循环结束后直接设 `is_enable=1`，不等待所有电机成功应答。因此内部 is_enable=1 只表示初始化发送路径已走过，不表示实际电机全部使能成功。

首次使能不使用 motor_enable 掩码。若只想控制一个电机，也不能据此推断只会使能该电机。

### 5.2 普通透传与全 FF 置零

`pack_motor_data()` 先复制 24 个槽的 8 B，然后检查所有配置为 INKEXBOT 或 LEADSHINE 的电机槽：

1. 只要其中任意一个槽不是连续 8 个 `FF`，整轮进入普通发送分支，向所有非 NONE 槽发送各自的原始 8 B。
2. 如果所有这两类有效槽均为连续 8 个 `FF`，进入置零分支。
3. 置零分支中，仅向 motor_enable 对应位为 1 的 INKEXBOT / LEADSHINE 电机发送 `0x7FF`、4 B、`00 nn 00 03`。
4. DMBOT 在置零分支仍发送其原始 8 B，不按该掩码选择。

所以“单个槽全 FF”并不足以触发该槽置零，必须满足全体相关有效槽的条件。普通数据模式下 motor_enable 不生效。置零后若继续用递增 hs 发送同样的全 FF 和非零掩码，将再次发出置零命令，没有独立的操作序号去重。

| `0x6000:0x21` | 226～227 | 2 | rx_error_can2 | UINT16 | 低8位普通错误计数，高8位FD数据段错误计数 |
| `0x6000:0x22` | 228～229 | 2 | rx_error_can3 | UINT16 | 低8位普通错误计数，高8位FD数据段错误计数 |
| `0x6000:0x23` | 230～231 | 2 | tx_error_can1 | UINT16 | 低8位普通错误计数，高8位FD数据段错误计数 |
| `0x6000:0x24` | 232～233 | 2 | tx_error_can2 | UINT16 | 低8位普通错误计数，高8位FD数据段错误计数 |
| `0x6000:0x25` | 234～235 | 2 | tx_error_can3 | UINT16 | 低8位普通错误计数，高8位FD数据段错误计数 |

`236 = 8 + 24×8 + 8 + 3×4 + 8×2`。这是线上的固定长度；C 结构体可能存在尾部对齐填充，主站不能直接以未经验证的宿主结构体 sizeof 代替 236 B。

### 6.1 未赋值字段

当前应用代码未发现对 `BufferIn.Cust.hs`、`hs_record`、`lz_3_error`、`lz_4_error` 的业务赋值。这些全局缓冲字段上电零初始化，正常代码路径下保持零。

不能把 Tx hs / hs_record 当作 Rx hs 回显、命令确认、采样序号或已完成动作标识。字段存在不代表其业务已经实现。

### 6.2 canN_error_log 位定义

can1/2/3 对应物理 CAN0/1/2。每路 32 位日志按下表解释，本路槽号 `j=0..7`。

| bit | 当前含义 | 更新方式 |
| --- | --- | --- |
| j，范围 0～7 | 本路第 j 槽在最近统计窗口未收到新的有效 8 B 反馈；1=缺帧 | 周期统计覆盖低 8 位；NONE 槽不报错 |
| 8+3j | 对应 LEADSHINE 电机的使能成功应答位 | 发送使能前清 0；成功回复置 1；失败回复清 0 |
| 9+3j | 对应 LEADSHINE 电机的置零成功应答位 | 发送置零前清 0；成功回复置 1；失败回复清 0 |
| 10+3j | 当前未使用 | 正常实现保持 0 |

例如 CAN1 上全局 ID 10 对应 can2_error_log，本路 j=1：bit1 为缺帧，bit11 为使能成功，bit12 为置零成功，bit13 未使用。

这不是厂家电机故障码。使能 / 置零成功位 0 同时可能表示“未请求、待回复、失败”，不能凭 0 区分三者；1 也可能是之前动作的结果，没有时间戳。

统计条件为 `if (joint_keepalive_time++ > 100)`，从 0 开始每 **102 次 motor_ctl_task 调用**执行一次，不是固定 100 ms。若实际每 1 ms 调用一次，约为 102 ms。即使 hs 未更新，只要 OutputMapping 继续被调用，统计仍推进；若 PDO 调用停止，该应用统计本身也停止。

缺帧时设置蜂鸣器和 LED，无缺帧时复位。未看到此统计函数主动停止电机。

### 6.3 CAN 错误计数

六个 rx_error_canN / tx_error_canN 都是 UINT16：

```text
低8位：rx_errcnt 或 tx_errcnt
高8位：fd_data_phase_rx_errcnt 或 fd_data_phase_tx_errcnt
```

它们在 `pack_motor_data()` 末尾读取硬件计数器并更新，不是每次 TxPDO 发送都自动刷新；首次使能返回、hs 被忽略或 control_word 不等于 1 时可能继续保留旧值。

## 7. CAN 回复如何进入 EC

### 7.1 普通反馈

CAN RX 中断调用 `receive_message_pack()`。运行状态为 MOTORCTL 时再调用 `pack_ethercat_data()`：

1. 仅当 `data_bytes == 8` 时接受为周期反馈。
2. 若 CAN ID 在 1～24，直接用它作为槽号。
3. 若 CAN ID 不在 1～24，尝试使用 data[0] 作为槽号。
4. 最终槽号在 1～24 时，将 8 B 原样复制到 `BufferIn.Byte[8+(id−1)×8]`，并递增该槽接收计数。

反馈只更新相应槽，不清空其他槽。没有每槽有效位、采样时间或数据年龄；旧反馈在断线后仍可能保留，主站应结合低 8 位通信日志，且不能把它当作精确的实时有效性证明。

这里没有把 CAN 通道一起用于最终槽路由校验，默认 LEADSHINE 的全局唯一 ID 与邮箱过滤承担主要约束。DMBOT 接收 ID 配为 `n | 0x10`，某些结果仍落入 1～24，可能绕过 data[0] 回退而映射到其他槽；该分支需要单独验证，不能以默认 LEADSHINE 行为推断其兼容性。

12 B CAN FD 反馈、2/3/4/6/7 B 厂家应答不会进入普通 motor_n 反馈槽。当前协议因此不构成任意长度 CAN FD 报文透明传输。

### 7.2 专用使能 / 置零反馈

`receive_motor_reply()` 使用邮箱 16，接受条件同时包括：

- 最近接受的 control_word 为 1。
- 标准数据帧，CAN ID=`0x7FF`，长度恰为 4 B。
- data[2]=`0x01`，data[3] 为 `0x06`、`0x03` 或 `0x00`。
- 电机 ID 按 `(data[0]<<8)|data[1]` 解析，范围 1～24。
- 电机所属 CAN 通道与实际接收通道一致，类型为 LEADSHINE。

| 载荷 | 含义 / 处理 |
| --- | --- |
| `ID_H ID_L 01 06` | 使能成功，置对应使能成功位 |
| `ID_H ID_L 01 03` | 置零成功，置对应置零成功位 |
| `ID_H ID_L 01 00` | 失败，依据全局 last_motor_command 判定清除哪类成功位 |

这类应答只更新 canN_error_log，不写入 motor_n 原始反馈槽。失败码没有自带操作类型，代码使用一个全局 last_motor_command，因此迟到失败应答可能被关联到后来的批次；没有事务 ID、超时状态或严格逐请求对应关系。

## 8. PDO、SDO 与应用回调的实际关系

```text
RxPDO → APPL_OutputMapping
       → memcpy 208 B 到 BufferOut
       → motor_ctl_task → hs门控 → control
       → 首次使能，或 pack_motor_data → 三路CAN邮箱

CAN RX中断 → 更新 BufferIn 中对应电机槽 / 日志
TxPDO ← APPL_InputMapping ← memcpy BufferIn 的前236 B
```

`APPL_GenerateMapping()` 通过分配对象和映射条目的低 8 位计算位数，最终转换为字节数。`APPL_InputMapping()` / `APPL_OutputMapping()` 的实际拷贝使用固定 MAX_PD_INPUT_SIZE / MAX_PD_OUTPUT_SIZE，而不是按主站动态选择的长度。

`APPL_Application()` 没有业务逻辑。Start/Stop Input/Output Handler 均直接返回成功；`APPL_StopOutputHandler()` 没有主动发送电机失能或复位应用使能状态。SSC 的 EtherCAT 状态机 / 看门狗行为不能等同于已经实现了电机侧停机动作。

对象字典中的 `Inputs0x6000`、`Outputs0x7010` 与应用缓冲 `BufferIn`、`BufferOut` 是不同变量。当前代码未发现两者同步，也没有自定义读写回调把它们连起来。因此：

- SDO 读取 `0x6000` 不能保证得到实时 PDO 反馈。
- SDO 写入 `0x7010` 不等同于周期命令下发，也不会自动调用 motor_ctl_task。
- CoE 栈支持 SDO，不意味着已经存在“SDO 透传厂家参数”的应用服务。

此外，`0x6000` 中部分已被固定 TxPDO 映射的条目未声明 OBJACCESS_TXPDOMAPPING 标志。固定映射表、ESI 与读写属性存在需要复核的差异；本稿记录实际映射，不推断支持动态重映射。

## 9. 主站使用流程与字节示例

### 9.1 初始化到正常发送

1. 核对实际设备身份与 ESI，处理 Product Code 不一致的问题。
2. 分配完整的 208 B 输出和 236 B 输入，不因仅配置了 10 或 15 个电机而缩短。
3. 根据编译分组和厂家协议准备各槽的安全报文，lz_3 填 0。
4. 以 hs=1、control_word=1 发起初始化使能；该次只走使能路径，不转发普通 motor_n 数据。
5. 检查实际 CAN 反馈和专用日志位。不能只把 is_enable 或 OP 状态视为动作成功。
6. 后续 hs=2、3、4……，保持 control_word=1，发送正常厂家编码的 8 B 槽数据。

启动代码在初始化后延时 5 秒并执行阻塞自检。自检失败仍将运行状态设为 MOTORCTL，不能把“进入运行”作为全部电机在线的证明。

### 9.2 输出尾部示例

下面仅展示 EC 标量字段编码。设 hs=2、control_word=1、motor_enable=0、lz_3=0，各 motor_n 必须另行按实际厂家协议填写。

```text
偏移0..7     hs           = 02 00 00 00 00 00 00 00
偏移8..199   motor_1..24  = 24 × 8 B 厂家报文
偏移200..201 lz_3         = 00 00
偏移202..203 control_word = 01 00
偏移204..207 motor_enable = 00 00 00 00
```

motor_enable=0 不会屏蔽普通电机报文。

### 9.3 选择性置零示例

在初始化使能批次之后，先按实际操作条件确认允许置零。把所有已配置的 LEADSHINE / INKEXBOT 槽都填为 `FF FF FF FF FF FF FF FF`，设置新的 hs、control_word=1，并选择 motor_enable 位。

例如选择全局 ID 1 和 ID 9：motor_enable=`0x00000101`，EC 字节为 `01 01 00 00`。默认分组中两者均有效，MCU 将分别在 CAN0 / CAN1 发送：

```text
CAN ID=0x7FF，4 B：00 01 00 03
CAN ID=0x7FF，4 B：00 09 00 03
```

分别检查 can1_error_log bit9 和 can2_error_log bit9。置零请求不能持续用新 hs 重复发送后又把其视为一次操作。

## 10. 已确认的实现边界

| 项目 | 现状与影响 |
| --- | --- |
| 固定容量 | 24 槽、208/236 B；与灵巧手 21 关节协议不兼容 |
| 统一运动单位 | 没有；EC 仅携带厂家原始 8 B |
| Product Code | 固件4、ESI1，需与实物核对 |
| control_word=0 | 不发送数据，不等于主动失能 |
| motor_enable | 仅置零选择，不是普通控制使能掩码 |
| 指令丢失保护 | 没有独立的应用层 hs 超时停机逻辑 |
| 输出停止回调 | 没有电机失能业务 |
| 反馈新鲜度 | 无采样序号 / 年龄；只提供按调用次数统计的缺帧位 |
| Tx hs / hs_record | 未实现回显，不用于请求确认 |
| 扩展 CAN FD 反馈 | 12 B 等非8 B普通反馈不能上传 |
| 原子快照 | ISR 直接写 BufferIn，InputMapping 直接拷贝；未见双缓冲或整体快照保护，不保证全部字段同时采样 |
| 专用回复关联 | 使用全局 last_motor_command，迟到失败回复关联存在歧义 |
| 其他厂家分支 | 不是默认配置；DMBOT 路由与 INKEXBOT 使能 / 成功反馈需另行验证 |
| SDO 实时数据 | 字典变量与过程缓冲分离，无已实现的异步厂家参数代理 |

以上为源码行为总结，不代表已完成对应修复。本次仅新增文档，没有修改参考工程的协议或固件。
